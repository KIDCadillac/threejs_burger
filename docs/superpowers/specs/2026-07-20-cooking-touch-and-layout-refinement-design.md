# 3D 做菜触控与布局体验改造设计

日期：2026-07-20

## 目标

针对公网手机试玩反馈，集中修正六个直接影响操作感的体验问题：加载状态不明确、料理台默认显得过小、上下旋转方向相反且过敏、食材落盘时突然变大、放回原料格不灵敏、叠放层级不受玩家控制。玩家主动拉近观察食材是需要保留的能力。

本轮不扩展新菜谱、联网或角色动画，只把现有汉堡料理台打磨成清楚、稳定、可预测的基础做菜框架。

## 已确认的根因

1. 页面只有一句静态“正在摆好料理台”，没有阶段、进度或耗时；并且加载层在同步创建场景后立刻隐藏，没有等待首帧真正绘制。
2. 手机镜头必须完整容纳宽 10.6 个世界单位的桌面，导致中央餐盘和食材只占较小面积。
3. 环绕镜头使用 `pitch - dy * sensitivity`，因此上下拖动与用户预期相反；默认灵敏度 `0.006` 也偏快。
4. 原料格食材缩放为 `0.54`，餐盘食材缩放为 `1.0`，吸附动画必然造成明显变大。
5. 放回检测使用与料格几乎相同的 `0.59 × 0.59` 半尺寸，并只认可精确落入自己的料格，手机手指很容易错过。
6. 餐盘层级用落点的世界坐标 X（左右位置）计算 `targetIndex`，所以看似相同的叠放会被插入不同层级。

## 方案比较

### 方案 A：只调参数

拉近镜头、放慢旋转、扩大料格、统一缩放。实现快，但层级仍缺少明确意图，玩家依然不知道食材会落在上面还是下面。

### 方案 B：确定性辅助吸附（采用）

保留轻量 Three.js 交互，不加入物理引擎；统一食材比例并扩大命中区，同时把餐盘分成可理解的“上层”和“下层”意图区。拖动时显示当前吸附意图，松手后严格按预览执行。性能稳定，手机触控也可预测。

### 方案 C：完整刚体物理

让食材依靠碰撞自然堆叠。自由度最高，但薄片食材容易穿透、抖动和翻飞，手机性能与网络体积成本也明显增加，不适合作为当前基础框架。

## 详细设计

### 1. 明确加载过程

- 加载层显示旋转指示器、百分比进度条、当前阶段文字和已等待秒数。
- 阶段依次为“连接料理台”“准备 3D 食材”“摆放工具”“完成首帧”。
- 百分比在真实阶段之间平滑推进，但不会在场景未就绪前显示 100%。
- 场景创建后等待至少一个动画帧，再显示 100% 并淡出加载层，避免黑屏或加载层消失后仍空白。
- 加载超过 8 秒时显示“网络较慢，仍在继续加载”，不让玩家误以为卡死。

### 2. 放大可操作区域

- 手机竖屏的 3D 舞台高度改为视口相关高度，目标为约 `72dvh`，同时保留合理的最小和最大值。
- 镜头更靠近中央餐盘，允许桌面最外沿轻微裁切，但七个原料和四个调料必须仍能看见和触达。
- 中央备餐板在 390 像素宽手机上至少占约 58% 的屏幕宽度，食材保持足够大的触控目标。

### 3. 旋转手势

- 左右方向保持现状。
- 上下方向翻转：手指向下拖时镜头视角向下跟随，手指向上拖时视角向上跟随。
- 默认灵敏度从 `0.006` 降低到约 `0.0042`，并保留现有俯仰边界，避免翻到桌底。
- 料理模式传入专用旋转边界：俯仰约限制在 `0.50–0.95`，水平旋转约限制在 `±0.78`；缩放距离保留 `6–32` 的宽范围，允许玩家主动贴近检查食材，也能拉远查看全台。
- 双指缩放和食材扭转逻辑保持不变。

### 4. 食材比例一致

- 原料格、拖动中、餐盘和叠放状态共用一个展示缩放值，不再在吸附时放大。
- 第一版采用 `0.72` 作为统一比例；相应增大料格视觉底座，使食材边缘可以自然略微伸出料格，但不与相邻食材严重重叠。
- 吸附动画只改变位置和旋转，不改变缩放。

### 5. 灵敏放回原料格

- 自己的原料格增加不可见触控磁吸区，半尺寸由约 `0.59` 提升到约 `0.95`。
- 食材进入磁吸区时高亮自己的料格，并显示“放回原料格”；松手后自动回正到原位置。
- 落在相邻料格附近但未进入自己的磁吸区时不误放，仍回滚到拖动前位置。

### 6. 玩家可决定叠放层级

- 删除“根据左右位置计算层级”的规则。
- 餐盘靠屏幕上方的半区表示“放在最上层”；靠屏幕下方的半区表示“塞到最下层”。中央缓冲区默认放在最上层，避免小幅手抖改变结果。
- 拖动食材进入餐盘时，显示清楚的意图提示：“放在最上层”或“塞到最下层”。
- 松手后的真实层级必须与松手前最后一次预览完全一致。
- 从现有汉堡中拿起食材重新放置时遵守同样规则，因此玩家可以按自己的顺序重排。

## 状态与组件边界

- `cooking-loader.mjs`：只管理加载阶段、耗时和首帧完成，不参与游戏状态。
- `cooking-interaction-controller.mjs`：只负责指针、镜头和拖动事件，修正俯仰符号与灵敏度。
- `cooking-solo-stage.mjs`：负责磁吸命中、顶部/底部意图和统一比例，是本轮叠放规则的唯一来源。
- `cooking-solo-app.mjs`：把当前拖放意图渲染成玩家可见提示。
- `cooking-workbench-3d.mjs` 与 `cooking.css`：负责更大的视觉工作区和料格，不改变料理状态。

## 错误处理

- WebGL 或模块加载失败时停止进度动画，保留明确错误层和重试建议。
- 页面进入后台、指针取消或 WebGL 上下文丢失时继续沿用现有回滚策略，食材必须回到拖动前的精确位置。
- 加载计时器、动画帧和事件监听在页面卸载或启动失败时全部清理。

## 验收标准

1. 390×844 手机视口能看到明确加载百分比、阶段和已等待时间，加载层在首帧后才消失。
2. 同一台手机上中央备餐板明显比当前版本大，所有原料和调料仍可触达。
3. 左右旋转方向不变；上下拖动方向与手指一致，单位位移造成的角度变化比当前版本更小。
4. 上下旋转达到边界后不会翻到桌底；双指缩放仍可主动贴近检查汉堡细节，也可拉远查看整张料理台。
5. 任一食材从原料格拖到餐盘，缩放前后完全一致，动画过程中也不改变缩放。
6. 在自己料格外围更宽松的区域松手可以成功放回，并有高亮或文字反馈。
7. 餐盘左右落点不再改变层级；上方意图区总是放到最上层，下方意图区总是放到最下层，预览与结果一致。
8. 原有拖动、双指缩放、双指扭转、加酱、撤销、重置和完成流程不回归。

## 测试策略

- 先为旋转方向、灵敏度、统一缩放、扩大磁吸区和确定性层级写失败测试。
- 为加载阶段状态机写独立单元测试，并覆盖成功、慢加载、失败和清理。
- 运行全部 Node 与 Python 测试。
- 在 390×844 的真实浏览器中验证加载层、台面占比、拖放顶部/底部、放回料格和控制台错误。
- 部署到 GitHub Pages 后再次在公网链接进行相同的手机尺寸验收。
