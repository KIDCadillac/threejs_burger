# 汉堡自动存档、视频反馈与高光回放设计

## 目标

把当前原型从“刷新就丢失、反馈只能看低清 GIF”升级为可持续测试的游戏框架：同一设备再次打开页面时自动恢复汉堡；错误反馈附带清晰且体积受控的视频；游戏主动捕捉可观看、可分享的高光片段。

本阶段不要求账号云存档。汉堡存档先绑定当前浏览器的本地存储；主动重置才清除，刷新、退出、切菜谱、完成料理都保留。

## 60 层堆叠

- 全局唯一上限为 60 层，HUD、状态机、反馈元数据、存档校验和相机适配必须共用同一常量。
- 第 60 层允许装盘，第 61 层必须被拒绝并给出可理解反馈。
- 相机不能只按经验距离后退，必须投影实际汉堡包围盒并在横屏、竖屏、不同俯仰角及重置镜头后保持可见。
- 反馈保留最多 60 层完整顺序，不再截断为 20 层。

## 自动存档

### 数据边界

新增版本化存档 envelope，至少保存：

- 已装盘顺序、每个实例的材料与旋转；
- 当前预备区来源、物理槽归属与库存；
- 酱料笔划；
- 当前菜谱、完成状态和实例序号；
- 当前工作台 loadout 的稳定槽位引用。

不保存撤销历史。60 层和多条酱料笔划会让历史快照快速耗尽 localStorage；恢复后从当前状态重新开始历史即可。

### 写入与恢复

- 状态对象发生变化后 150ms 防抖写入，`pagehide` 与销毁前立即 flush。
- 启动时在首次建立 3D 模型和控制器前解码、验证并恢复，避免先显示空桌再跳变。
- 非法 JSON、未来版本、61 层、重复引用、非法数值或损坏笔划全部忽略，并以全新汉堡启动；不能让坏存档卡死页面。
- 存储读取、写入、删除或容量异常都不得回滚游戏操作。
- “重新开始/重置”先取消待写任务，再删除汉堡存档；工作台槽位配置和验收参数继续保留。

## 视频反馈

### 格式选择

优先使用浏览器原生 `MediaRecorder`：

1. `video/webm;codecs=vp9`
2. `video/webm;codecs=vp8`
3. `video/mp4;codecs=avc1.42E01E`
4. `video/mp4`

逐项用 `MediaRecorder.isTypeSupported()` 检测，不按设备名称猜测。只有设备完全不支持视频录制时才回退 GIF。

### 质量与体积

- 视频目标 480px 宽、12fps、6 秒，视频码率约 750kbps；目标体积约 0.6MB，最大上传限制 8MB。
- 录制画面来自 WebGL canvas 的 `captureStream()`；截图仍单独上传，便于快速预览。
- 反馈弹窗明确显示“正在生成 WebM/MP4 视频”或“设备不支持视频，正在生成兼容 GIF”，不再统一写 GIF。
- 同一反馈会话网络失败后复用已经生成的视频，不重复编码。
- Apps Script 只接受显式白名单 `video/webm`、`video/mp4`、`image/gif`，按真实 MIME 保存正确扩展名，拒绝伪造类型。

## 高光回放

高光不是反馈 GIF 的别名，而是独立的游戏功能。

### 捕捉窗口

- 保留最近 5 秒的画面环形缓冲；触发后继续捕捉 3 秒，生成约 8 秒完整片段。
- 首版触发条件：完成料理，以及装到第 10、20、40、60 层。
- 同一触发只生成一次；片段生成期间不阻塞继续操作。
- 内存预算受控：预览缓冲只保存缩放后的帧，生成完成后及时释放原始像素。

### 展示

- 页面提供“高光回放”入口；没有片段时显示等待提示，有片段后显示触发名称和时间。
- 使用 `<video controls playsinline>` 播放；可下载，支持 Web Share API 时可调用系统分享。
- 高光片段首版保存在当前会话内，不写进汉堡 localStorage。刷新后汉堡仍在，高光可以重新通过继续游戏生成；云端/IndexedDB 高光库放在后续版本。

### 视频生成机制

为保证“触发前”画面真实存在，帧环形缓冲保存带时间戳的缩放画面。触发时冻结前 5 秒快照，再采集后 3 秒，通过离屏 canvas 按时间顺序回放，并用 `MediaRecorder` 编成一个自包含视频文件。这样不会拼接缺少容器头的 WebM/MP4 分片。

## 降级与错误处理

- `captureStream` 或 `MediaRecorder` 缺失：反馈退回 GIF；高光入口说明当前浏览器仅支持兼容回放。
- 视频编码超时或失败：反馈可自动改用 GIF；高光保留可重试状态，不影响游戏。
- 上传超时后缓存 Blob；用户重试只重发。
- 录制、导出和上传各自使用独立状态，文案不能把“请求已提交”误写为“云盘已保存成功”。

## 验收

1. 叠到 60 层仍完整可见，第 61 层被拒绝；HUD 与反馈均显示 60。
2. 叠放、旋转、涂酱后刷新页面，首次 3D 渲染即恢复相同汉堡；只有重置会清空。
3. Chrome/Android 优先生成 WebM，支持 MP4 的 Safari 可生成 MP4；生成文件可由 `<video>` 播放，6 秒目标体积明显小于同清晰度 GIF。
4. 完成料理和 10/20/40/60 层至少各触发一次高光；片段包含触发前约 5 秒及触发后约 3 秒。
5. 不支持视频的测试环境仍可生成 GIF 反馈，原有上传超时与重试语义不回归。
6. 全量 Node、Python、浏览器移动端验收与 `git diff --check` 全部通过后才能部署。
