# 实时 3D 烹饪与人物反应返工设计

日期：2026-07-20

## 目标

把现有部署与揭晓场景从 WebP、PNG、SVG 和 CSS 拼接动画，替换为可在手机浏览器实时运行的三维体验。玩家必须能亲手拆开、移动、旋转并重新组合汉堡，把不限两种的调料拖放到任意夹层；揭晓时，普通卡通人物必须用三维手臂拿起食物、咬下，并以面部、身体和特效共同表现喷火、难受等反应。

“女巫的毒药”只是玩法模式名称，不限定人物身份、服装或世界观。视觉采用低多边形、卡通偏真实、暖色料理台的风格，借鉴烹饪游戏清晰、夸张、有节奏的操作反馈，但不复制具体游戏的角色、模型、场景或界面。

## 本轮交付范围

本轮先完成一个从头到尾可玩的三维纵向样例：

1. 进入“和电脑玩”。
2. 在三维料理台选择汉堡。
3. 旋转观察汉堡，掀开顶层并移动至少三个独立夹层。
4. 拿起调料瓶，把辣椒酱、芥末、酸汁或黏酱拖到任意夹层；允许重复添加和混合添加。
5. 把汉堡重新组合并确认部署。
6. 电脑选择食物后进入揭晓。
7. 三维人物伸手拿起汉堡、送到嘴边、咬下。
8. 辣椒酱触发完整的停顿、皱脸、身体后仰、张嘴喷火、流泪与恢复动画。
9. 玩家可回放部署和人物反应。

现有单人模式、匹配、邀请好友、房间、回合、陷阱归属和电脑对手规则继续保留。本轮不扩展新的食物种类，也不制作商店、皮肤、武器或商业化系统。

## 视觉与镜头

### 部署场景

- 采用暖色木质料理台、盘子、柔和阴影和近景俯视镜头。
- 核心操作区只使用实时三维物体；食物、手、工具、锅具和调料不得由静态图片冒充。
- 汉堡材料使用卡通写实比例和材质：面包有烘烤色、肉饼有不规则边缘、芝士有软垂角、蔬菜有厚度、酱料有光泽。
- 可使用 CSS 绘制外围按钮和文字，但不得用背景图片伪造料理台或食物。

### 揭晓场景

- 镜头先给汉堡近景，再切到普通卡通人物的半身正面。
- 人物具有可独立运动的头、躯干、上臂、前臂、手、眼球、眼睑、眉毛和嘴。
- 表情语言依靠眼神、眉形、嘴形、头部和肢体共同完成，不使用 emoji、贴纸或静态表情包。
- 喷火使用三维粒子或几何体；眼泪、汗滴和热浪也由实时特效生成，不使用序列图片。

## 三维交互

### 镜头手势

- 在空白处单指拖动：绕汉堡旋转镜头。
- 双指缩放：拉近或拉远。
- 双击“复位”：回到标准俯视角度。

### 食物手势

- 按住食材：高亮该三维夹层并显示轻微抬起反馈。
- 拖动食材：沿料理台平面移动；松手后落下并吸附到最近的合法夹层位置。
- 垂直拖动或点击“打开”：展开汉堡各层，方便精确加料。
- 每层都是独立对象，拥有稳定标识、位置、旋转、层序和酱料记录。
- 非法重叠、拖出料理台或夹层顺序错误时，物体弹回上一个合法位置，并给出短震动和文字提示。

### 调料手势

- 调料瓶是可拿取的三维物体。
- 玩家把瓶口拖到目标夹层上方并保持倾斜，酱料沿拖动轨迹落下。
- 同一种调料可以多次添加，不同调料可以混合，不设置“两种上限”。
- 单局用部署倒计时控制复杂度，而不是人工限制调料数量。
- 每条酱料轨迹记录调料类型、目标夹层、相对坐标、长度和用量，供揭晓回放及反应强度计算。

## 人物动作与反应

动画时间轴由状态驱动，而不是替换图片：

1. `notice`：看见选中的食物，目光移向汉堡。
2. `reach`：肩、肘、手腕依次运动，小手伸向汉堡。
3. `grip`：手指收拢，汉堡绑定到手部抓取点。
4. `lift`：汉堡随手移动到嘴边，头部轻微迎上。
5. `bite`：嘴张开、头前探、汉堡出现三维咬痕或缺口。
6. `chew`：下颌与脸颊运动，眼睛观察味道变化。
7. `suspense`：短暂停顿，人物意识到不对劲。
8. `burst`：根据主要调料播放喷火、喷嚏、酸缩或黏嘴反应。
9. `recover`：擦眼泪、捂嘴、扇风或拉开黏丝。
10. `settle`：恢复待机，但保留轻微余波表情。

首个纵向样例完整制作辣椒反应。芥末、酸味和黏味先接入同一状态机和强度数据，后续按同样骨架补齐专属动画，不复制辣椒动作。

## 技术架构

### 渲染层

- 使用本地随应用发布的 Three.js/WebGL 模块，不从公共 CDN 临时加载。
- 一个渲染管理器负责画布、相机、灯光、阴影、尺寸变化、帧循环和资源释放。
- 部署场景和人物场景共用渲染基础设施，但拥有独立场景控制器，避免一个大文件同时管理全部行为。
- 首版三维模型由程序化几何体和独立节点组合，确保立即拥有真正的三维旋转、层级和动画能力；接口预留为以后替换精细 GLB 模型而不改玩法逻辑。

### 组件边界

- `BurgerModel`：创建夹层、展开/合拢、合法吸附、咬痕和调料锚点。
- `CondimentTool`：调料瓶抓取、倾斜、轨迹采样和酱料网格生成。
- `CookingInteractionController`：触控命中、拖动、镜头手势、撤销与复位。
- `CharacterRig`：人物骨架节点、面部参数、手部抓取点和待机动作。
- `ReactionDirector`：消费反应数据并驱动完整动作时间轴。
- `ThreeSceneHost`：管理 WebGL 生命周期、手机性能档位、暂停与销毁。

### 数据流

部署操作只上传可验证的小型结构化数据：食物类型、夹层最终顺序、调料轨迹摘要、调料总量和动作时间。服务端仍然只在当前玩家的秘密部署阶段返回自己的陷阱细节；对手只能看到普通人物动作和表情，不能看到被选择的零食或夹层。揭晓时服务端返回必要的公开结果，客户端据此重建三维回放和人物反应。

## 移动端与性能

- 支持近期 iPhone Safari、Android Chrome 和桌面 Chromium 浏览器。
- 竖屏优先，横屏仍可操作。
- 目标是在常见中端手机保持稳定的 30 FPS，性能充足时运行 60 FPS。
- 限制实时灯光、阴影分辨率、粒子数量和模型面数；页面退到后台时暂停渲染。
- WebGL 不可用时显示明确的设备不支持提示，不回退到图片版本。
- 触控目标、拿取反馈和撤销操作必须适合单手使用。

## 错误处理

- 模型或三维模块加载失败：显示可重试提示，并保留返回大厅入口。
- WebGL 上下文丢失：暂停回合画面，尝试恢复一次；失败则提示重新进入。
- 网络短暂断开：保留尚未确认的本地操作，重连后根据服务端阶段决定恢复或丢弃。
- 非法夹层、调料或轨迹数据：服务端拒绝，不进入揭晓，并返回可读错误。
- 动画被切页或回放打断：取消旧时间轴、解除手部绑定、释放三维资源，避免重复人物和残留音效。

## 远程试玩与安全

- 验收必须提供公网 HTTPS 链接，苹果和安卓浏览器可直接打开；局域网地址不算完成。
- 测试服务只暴露游戏需要的 HTTP/WebSocket 路径，不暴露工作区文件、终端或管理接口。
- 房间号和玩家标识使用不可预测值；对连接、建房和消息频率做限制。
- 服务端验证所有三维部署摘要和回合命令，不能信任浏览器提交的胜负或秘密结果。
- 临时测试链接用于验收，测试结束后可关闭；正式上线需要独立域名、持久化部署、监控和更完整的防滥用策略。

## 验收标准

以下条件必须全部满足：

- 浏览器开发检查可确认核心场景由 WebGL 画布实时渲染，不是背景图、视频、SVG 食物或 SVG 人物。
- 汉堡至少包含七个可独立变换的三维夹层。
- 用户能旋转视角、展开汉堡、移动至少三个夹层并重新叠放。
- 四种调料均能通过拖动和倾斜加入任意夹层，允许重复和混合。
- 调料轨迹在三维夹层表面可见，并影响辣椒反应强度。
- 人物真实完成伸手、抓取、抬起、张嘴、咬下、咀嚼、停顿、喷火和恢复动作。
- 面部变化由三维眼睛、眉毛和嘴部节点驱动，不依赖 emoji 或表情图片。
- 单人模式能从部署完整玩到揭晓并回放。
- 公网 HTTPS 地址可由不同网络下的手机打开，并能正常使用 WebSocket。
- 规则单元测试、状态转换测试、部署数据验证测试和浏览器触控流程测试全部通过。

## 明确不做

- 不照抄《潜水员戴夫》或截图中游戏的模型、角色、界面、音效和关卡。
- 不继续完善旧的 SVG 人物或二维食物拼图。
- 不在本轮制作所有零食和所有反应的精细三维版本。
- 不在本轮建设正式商业上线所需的账号、支付、广告、排行榜、审核素材和运营后台。
